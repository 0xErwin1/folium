# RCO-006 reader-first SAF evidence

This is the corrective-pass evidence for RCO-006 / RF-1. It supersedes the prior
version of this document, which claimed a PASS on `emulator-5556` that could not
be reproduced, and a later revision of this document, which claimed the
`PermissionRevoked` instrumented flake was closed after two runs — it was not; see
"Instrumented stability" below for the full history and the corrected root cause.
Unless a table row states otherwise, its numbers were measured in the session that
added that row; sessions are distinguished throughout this document.

## Quick path

1. `bind()` no longer gates on the returned Intent's flags; `takePersistableUriPermission`
   is the sole source of truth for the grant (see "What changed").
2. The instrumented grant is now taken by `SafPickerHostActivity.onActivityResult`, while
   that activity is still alive, closing a separate harness race that caused an
   intermittent `PermissionRevoked` failure on both emulators — see "Instrumented
   stability" for the diagnosis, the fix, and the multi-run sampling evidence.
3. See "Measured result" and "Instrumented stability" for exact counts, skip status,
   and elapsed time, read from the UTP XML under `androidTest-results/connected/debug/`.

## What changed in this pass

| Area | Fix |
|---|---|
| `SafGrantRepository.bind()` | Removed the pre-check that gated on the returned Intent's grant flags before calling `takePersistableUriPermission` (that parameter was later deleted entirely by the pre-RCO-009 cleanup batch — `bind()` now takes only `treeUri`). `ACTION_OPEN_DOCUMENT_TREE` only guarantees grant flags on the *request* Intent, not the result; gating on the result rejected legitimate grants as `PermissionRevoked` and was device-dependent (failed on `emulator-5556`, passed on `emulator-5554`) in the sampling available at the time. This was a real defect and removing the gate was correct, but it was not the whole cause of the `PermissionRevoked` failures observed under this test — see "Instrumented stability" below. |
| `SafGrantRepository.probePdfCandidates()` | A single document's `RuntimeException` (e.g. from `openFileDescriptor` or a malformed cursor read) is now caught and recorded as a typed per-document `DocumentUnreadable` skip, instead of escaping to the outer catch and invalidating the whole root as `ProviderUnavailable`/`TransientQueryFailure`. |
| `verifyArchitectureNegative` (`build.gradle.kts`) | The permission negative used to build its "forbidden" manifest string from the permission under test, so it always passed regardless of whether the real guard worked. It now writes an isolated fixture manifest file per permission and calls the same `manifestForbiddenPermissions()` function the positive check uses, so a broken guard fails the negative. Also fixed a literal `\n` (backslash-n) written into the SAF-leak fixture instead of a real newline. |
| `LibraryIdentityTest` | Replaced a tautological identity assertion (both sides built from identical literals) with assertions that identity is stable across simulated rename/version changes and differs when authority or document ID differs. Removed an assertion on a string that was never inserted. |
| `SafGrantRecoveryTest` | Replaced 2-of-8 `RecoveryReason` coverage with an exhaustive check driven off `RecoveryReason.entries`, so a newly added reason fails the test until it is mapped. |

## Instrumented stability

A later verification pass ran `:app:connectedDebugAndroidTest` 8 times across both
emulators and found `SafRealGrantInstrumentedTest` failing 3/8 (37.5%) — on both
`emulator-5554` and `emulator-5556` — with `AssertionError: bind failure=PermissionRevoked`
at `SafGrantRepository.bind()`, stage `Grant` (`SecurityException` from
`takePersistableUriPermission`). The returned-flags gate removal above was a real
fix but did not close this failure; `bind()`'s body was byte-identical to the
version that already showed the failure, so the gate removal was ruled out as the
cause.

**Root cause**: the transient URI grant from `ACTION_OPEN_DOCUMENT_TREE` is owned by
the activity that receives the result. The test's picker harness
(`SafRealGrantInstrumentedTest.selectWithDocumentsUi`) ran the picker inside
`ActivityScenario.launch<SafPickerHostActivity>(...).use { }` and read the result
only after that block closed and destroyed the activity; the system asynchronously
releases the grant once the receiving activity is destroyed, and `bind()` — called
after the block — raced that release. The revocation was observed landing with a
zero-millisecond gap to `bind()`, so no sleep, poll, or retry could have fixed it;
the fix has to keep the grant while the activity is alive, not wait it out.

**Fix**: `SafPickerHostActivity.onActivityResult` now calls
`takePersistableUriPermission(treeUri, FLAG_GRANT_READ_URI_PERMISSION)` itself,
while the activity is still alive, immediately after receiving the picker result.
This is also the correct production pattern: when the real Compose picker is wired
in RCO-009, the persistable grant must be taken in the activity result callback,
not deferred to the repository layer. `SafGrantRepository.bind()` was not changed;
its own `takePersistableUriPermission` call remains correct as written and now
succeeds because the grant is already held.

## What `SafRealGrantInstrumentedTest` proves

The production `ACTION_OPEN_DOCUMENT_TREE` intent is driven through Android DocumentsUI with UiAutomator selectors derived from the hierarchy. The provider-issued activity result is bound through the production repository with the returned-flags gate removed; its persisted permission is confirmed read-only (not write), survives repository reconstruction and an actual `ActivityScenario.recreate()`, and is revoked and cleared before an idempotent clear/rebind sequence.

The fixture checks actual root projection values/types and direct-child ancestry, including root-is-not-its-own-child and unknown negatives. The test proves stable root identity across a rename while root version changes, and stable PDF document identity while its version changes. It admits two readable `application/pdf` documents, including a non-PDF-like display name, excludes a text document named like a PDF and a directory, and reports unreadable and malformed children as typed per-document skips while retaining valid candidates.

This pass adds a fifth candidate-probe scenario (`Mode.UnstablePdf`): one document's `openFileDescriptor` call throws `IllegalStateException` while its sibling document remains openable. The result stays a `Candidates` result — the failing document is recorded as a typed `DocumentUnreadable` skip and the healthy document is still returned — proving per-document isolation rather than whole-root failure. Root malformed, unavailable, missing, and revoked cases remain typed root failures, unaffected by this change.

## Permission negative, verified non-tautological

To confirm `verifyArchitectureNegative` is a real guard and not a guard that trivially passes, the fix was validated by temporarily replacing `manifestForbiddenPermissions()` with a stub returning `emptyList()`: the negative task failed with `Permission guard did not reject isolated fixture manifest declaring android.permission.INTERNET`, as expected. The real implementation was restored immediately after, and `verifyArchitecture` + `verifyArchitectureNegative` were re-run to confirm both pass (see "Measured result").

## Scope of this pass

This corrective pass re-verifies only the items closed in this round: `SafGrantRepository.bind()`/`probePdfCandidates()`, `verifyArchitectureNegative`, `LibraryIdentityTest`, and `SafGrantRecoveryTest`. Broader release-build evidence (full online build/lint pipeline, OCR regression) from earlier RCO-006 verification rounds was not re-executed in this session and is not restated here as freshly measured.

## Privacy and log inspection qualification

Production code emits no URI, display name, or provider document identifier logs. DocumentsUI, UiAutomator, and UTP may emit self-authored **debug-only fixture** URIs, names, and IDs during the instrumented run; these are not user data. Consequently this report does not make an unqualified "logcat contains no identifiers" claim. This report uses opaque case IDs and deliberately reproduces no raw URI, provider document ID, or display name.
